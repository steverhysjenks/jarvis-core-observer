# Home Assistant nutrition summaries

Task 6A extends the existing Core process, without changing voice routing or creating a database. SparkyFitness v1.8.0 remains authoritative. No diary records, credentials or personal readings belong in this repository.

## Contract

GET `/nutrition/summary/today` and GET `/nutrition/summary/history` require `Authorization: Bearer <dedicated summary token>`. Only these routes accept that credential; it cannot access `/request` or mutate nutrition. A missing/incorrect token returns 401; missing configuration/disabled nutrition returns 503. POST is 405. HTTP is restricted to the existing trusted LAN; no public route is configured. Bearer credentials and nutrition data are plaintext on this LAN, consistent with existing service transport; do not expose these endpoints through a public proxy.

Today returns `date`, `goal_kcal`, `consumed_kcal`, `remaining_kcal`, `progress_percent`, `protein_g`, `carbs_g`, `fat_g`, `has_entries`, `timezone`, `updated_at`, `status` and provenance. Values come from native `sparky_get_nutrition_summary(date)` and `sparky_get_goal_snapshot(target_date)`. The latter uses Sparky's adjusted/effective goal, matching the existing conversational calculation. Remaining is that goal minus intake, and may be negative; progress is not capped at 100. Missing/invalid goals remain null. A zero goal remains zero with null percentage. An empty aggregate day has unknown intake, not an invented zero. Explicit source zero with a logged row remains zero.

History makes **one** `sparky_get_nutrition_summary(start_date,end_date)` call for 14 London calendar dates including today. It returns `timezone`, `window_days`, `start_date`, `end_date`, `days`, `logged_days`, `completed_logged_days`, `average_logged_day_kcal`, `average_includes_today=false`, `today_kcal`, `updated_at`, `status`. Each daily record has `date`, `calories_kcal`, `has_entries`, `is_today`, `status`. A source row indicates recorded nutritional intake (native aggregate semantics, including countable supplements where supported). Omitted dates have null calories, false `has_entries`, `no_entries`. Days with an ambiguous-unit warning have null calories and `unavailable`; this makes the top-level status partial and suppresses the average. The average includes only completed dates with recorded, usable intake; zero-valued logged rows count. Today is exposed separately and excluded from the average. `logged_days` includes today, while `completed_logged_days` counts usable completed days.

Source failure gives HTTP 503, status unavailable, `updated_at=null`, and null metrics. History still contains 14 dates, each with null `has_entries` and unavailable status, distinguishing failure from no entries. Malformed responses, duplicate/out-of-range dates and unsupported energy units fail closed. No individual food records are returned. Native v1.8.0 itself converts missing nutrient values to zero; this aggregate interface cannot reconstruct missing source provenance. The bridge does not advertise micronutrient completeness or invent alternative values.

## Refresh and freshness

HA has one shared REST resource for all seven daily entities (180 seconds), and one for both historical entities (7200 seconds). Core coalesces requests with a per-resource lock and caches successful payloads for 30 seconds, failures for 5 seconds. Both caches are memory-only and invalidated by a new Europe/London diary date. Source work has a 20-second overall timeout. Old success is never served after an expired refresh fails. Responses use `Cache-Control: no-store`. `updated_at` is the retrieval-start timestamp, not a claimed source modification time. HA rejects daily responses older than 240 seconds or for the wrong local date, and historical responses older than 7300 seconds. Native REST network failure marks entities unavailable. Midnight switches on the next poll; history incorporates the new date at its next scheduled two-hour refresh. No scheduler is added.

## HA configuration and credential lifecycle

Non-secret templates: `integrations/homeassistant/sparky_rest.yaml` and `recorder-exclusions.yaml`. Include the REST list from top-level `rest: !include sparky_rest.yaml`; preserve unrelated config. Merge all nine exact IDs into `recorder.exclude.entities` before activating sensors. Do not add these entities to InfluxDB. All numeric states use measurement rather than cumulative totals; their daily resets must not be interpreted as a lifetime counter. The 14 small daily records live only on the logged-days entity's attributes for a future ApexCharts `data_generator`; no Recorder history is needed. No dashboard edits are part of this rollout.

Generate a high-entropy token once on CT122. Store it root:jarvis 0640 at `/etc/jarvis-core/secrets/nutrition-summary.token`, with its path in the existing EnvironmentFile. On HA, append only `jarvis_nutrition_summary_authorization: "Bearer <token>"` to protected `secrets.yaml`. Never put actual values in YAML under Git, entity attributes, logs, command arguments or CI artifacts. The upstream existing read-scoped MCP key is reused only inside Core. Rotate by replacing the token file and HA secret together, then reload REST; Core reads the token file on every authorization, without requiring restart for rotation. Revoke by removing/replacing the dedicated file. The existing upstream token expiry remains governed by the nutrition runbook.

## Rollout, validation and recovery

Use the existing protected-main CI validation/regression/package/manual deploy/production acceptance gate in `docs/cd.md`. Do not install application code over SSH. Runtime secrets are external to releases. Before HA changes, retain root-restricted HA-local copies of configuration.yaml/secrets.yaml and record dashboard hashes. Validate with HA's installed config checker before a user-approved Core restart (Recorder exclusions require restart). Never edit `.storage`. Verify native REST config schema, exact entity IDs/units, matching native goal/aggregate values, authentication denial and no write access, bounded history attributes, freshness and poll intervals, unchanged dashboard hashes and active Recorder exclusions. Record production evidence separately from synthetic tests; do not commit personal readings.

Rollback HA by restoring its local configuration/secrets backup, validating and performing an approved restart. Disable REST polling before revoking its token. Core application rollback follows the established release symlink/controller procedure; no schema migration or persistent nutrition cache exists. Leave existing voice credentials unchanged. A rolled-back Core without summary routes makes these sensors unavailable rather than affecting the diary.

Acceptance pending deployment: offline regression and live API/HA evidence must both pass before completion.
