# Post-deployment production regression acceptance

This change adds an `acceptance` stage after the existing manually approved deployment. It neither deploys by itself nor changes bootstrap/preflight approval. `production_acceptance` is automatic only on protected-main push/web pipelines with JARVIS_OPERATION=deploy and a successful deploy_production job. It inherits the existing production environment, protected file-type SSH variables, strict verified host keys, noninterruptible execution and jarvis-core-lxc122 resource group. No job runs production tests for feature/MR pipelines or bootstrap-only operations.

## Version-matched sources and execution

package_release builds `tests.tar.gz` directly from Git objects at the exact validated SHA, separately from the application release archive. It includes all regression source, the explicit production profile, tooling requirements, runner and a TEST_RELEASE.json source-hash/commit manifest. It also records hashes for the corresponding application release files. CI compares the bundle/controllers independently against the same commit before transfer via the existing ansible SSH mechanism.

The deployment transport publishes results/deployment.json only after the deployment controller exits successfully, including activation/health verification. This receipt contains the validated commit, pipeline/job IDs and exact activated release directory; it contains no credentials. The acceptance job explicitly retrieves this artifact from its non-optional deploy_production dependency. Missing receipts, unsuccessful/skipped deployment receipts and receipts from another pipeline fail before SSH credentials are read.

The acceptance controller reuses the verified deployment controller and its host lock/preflight. It requires the active managed release to match the receipt's exact release directory, commit, application file map and actual file hashes before and after testing. It also checks the service's actual jarvis:jarvis credentials, cwd device/inode and stable MainPID, and rejects a PID change across testing. A healthy HTTP endpoint alone cannot satisfy release identity. If another deployment interleaves between the deploy and acceptance jobs, even a new release of the same commit is rejected. Resource groups lock individual jobs; they do not reserve the host across that gap. The shared host lock covers acceptance setup, tests and final verification, so cooperating deployments cannot change the release during execution. Manual root operations outside this lock remain an operational risk.

Tests run as jarvis:jarvis in a fresh /var/tmp/jarvis-acceptance-* scratch directory. A separate Python 3.13 test-tool venv installs only the version-matched acceptance requirements. The active release's actual runtime site-packages and source are used for application imports. Neither runtime venv nor app files are overwritten. The systemd transient test unit loads the same /etc/jarvis-core/jarvis.env as production; no secrets are sent to GitLab or stored in the bundle. Environment-file handling is delegated to systemd rather than parsing/sourcing secrets in a shell.

The unit uses NoNewPrivileges, ProtectSystem=strict, ProtectHome and private tmp. Only test work/results directories are explicitly writable. It runs a pytest entrypoint, never Uvicorn/ASGI lifespan, blocks app.main imports, server binds and subprocesses, and replaces the Observer loop with a refusal. The existing production Observer continues running; no second Observer is started. Cleanup stops only the named transient acceptance unit, never jarvis-core.service, and verifies it is inactive with MainPID=0 (including a collected/not-found unit) before removing its fresh scratch directory. If termination cannot be confirmed, acceptance fails and retains scratch for approved operator inspection; RuntimeMaxSec remains bounded. Cleanup errors also fail acceptance. No cleanup traverses application releases or persistent state.

## Read-only integration coverage

- Home Assistant: authenticated real state reads, plus the nine imported live context/Observer contract tests (states, places, calendars, history, availability and deterministic snapshot candidates).
- Music Assistant: bounded genres/library catalogue query through the existing native adapter. Its native API uses POST for this read-only command; playback and other commands are rejected.
- Local LLM: GET /api/tags and presence of the configured judgement model. No generation/inference runs automatically; this does not prove model judgement quality or inference performance.
- Observer: existing running service status, configured mode, completed cycles and no error.
- SQLite: exact mode=ro URI, query_only and SELECT-only authorizer for ledger-schema reads and delivery-history reads when that lazy table already exists. Existing deterministic ledger/delivery tests write only their temporary databases. No schema/data migration, backup or restore is performed.
- Jarvis API: loopback health/version, Observer status and context snapshot GETs. Request/replay/announcement APIs are never invoked.

HTTP interception checks every httpx request including redirects against explicit origins/methods/paths and the single allowed Music Assistant catalogue command. Ollama generation, HA service actions, Jarvis POSTs and other hosts are denied. SQLite audit/wrapper checks reject production write paths. These are Python-level checks for reviewed test code, not a network firewall or a sandbox for hostile native extensions. Network remains enabled to reach real integrations; do not claim container network isolation. OS read-only protections provide an additional filesystem boundary and fail setup if the LXC cannot support them.

## Behavioural exclusions and offline CI

The original five behavioural cases in test_qwen_live.py are packaged as evidence/source but ignored before collection and never imported automatically. A reviewed production module allowlist and marker checks apply even if a caller attempts a different -m option. Live network tests remain excluded from ordinary offline CI by its existing unmodified root guards/configuration. This production runner intentionally uses real configuration rather than those dummy CI settings.

## Results and failure semantics

JUnit XML is returned over the same verified SSH connection and uploaded as results/production.xml with artifacts:when=always. Test failures, skips/xfails, collection/guard failures, missing/empty/inconsistent results, active-version mismatch and transport/setup errors fail acceptance. Later identity/cleanup failures append a generic failure without discarding available testcase results. The transport fetches XML even when the remote command fails; if retrieval fails, it leaves the sanitized remote production.xml and its unique upload directory for approved operator retrieval/cleanup, while removing uploaded source/archive files. Safe fallback XML covers setup/transport failures where possible; SSH/job cancellation can still prevent retrieval or artifact upload. Raw test-process output is suppressed and JUnit failure payloads, captures/logs and live tracebacks are replaced with generic messages. Operators must use separately approved read-only inspection for detailed diagnosis.

A failed acceptance stage leaves the successfully deployed release running, marked unaccepted by the failed pipeline. It does not silently roll back a healthy release because an upstream integration failed. Existing application activation/health rollback protections remain unchanged. Code rollback still cannot undo SQLite migrations or runtime data mutations.

## Outstanding operational risks

Acceptance failures now include stage-specific safe diagnostics in logs and fallback JUnit: operation, exception class, subprocess exit code, fixed error classification, pytest/test-start markers and whether a real pytest JUnit file was produced. Stages distinguish preflight, bundle/release/process verification, test venv creation, dependency installation, active runtime inspection, scratch permissions, transient unit execution/cleanup and result verification. Raw subprocess output and exception messages remain suppressed. A nonzero systemd-run exit can describe either launch or test failure; the runner stage marker distinguishes how far Python/pytest reached. `tests_started=true` means pytest entered a testcase's execution protocol, including setup; it does not mean tests passed. Null startup fields mean no reliable runner marker was available. `junit_produced` excludes the controller's fallback XML, while transport `junit_retrieved` records fetching either report type.

Pipeline #23's generic CalledProcessError/fallback evidence does not establish the failing operation, or whether the controller itself failed in a subprocess. The CI exception can simply be SSH's nonzero remote-controller result. Successful independent venv/pip checks do not prove acceptance dependency installation succeeded; no acceptance journal entry is consistent with a pre-launch setup failure, but does not prove one. Package download/resolution failure, preflight commands, release checks and active-runtime inspection remain hypotheses until a version-matched approved run returns the new diagnostics. No retries, dependency-install bypasses, reduced sandboxing or deployment/rollback changes are introduced by this diagnostics correction.

The diagnostic failure message replaces the controller's existing fallback testcase instead of appending the same testcase ID. This also corrects a reporting defect: [GitLab ignores duplicate test names after the first](https://docs.gitlab.com/ci/testing/unit_test_reports/), which could leave the generic message visible while hiding the later diagnostic. Existing real testcases are retained.

Production execution has not been performed during implementation. Confirm systemd sandbox support, existing protected production variable/environment settings, package access and disk headroom before approval. SQLite WAL/SHM must be readable for mode=ro; a busy/unreadable database fails rather than enabling writes or using immutable mode that ignores current WAL. External integrations may fail transiently or contain changing data; imported historical assertions may therefore fail without a source regression. Test tooling uses pinned major-version ranges rather than a complete lockfile. The extraction used pytest 9.1.1 while current approved CI/tooling remains pytest 8.x; compatibility is pending real Python 3.13 CI/acceptance. Temporary state is removed after confirmed unit termination; termination uncertainty, cleanup errors and report-fetch failures require approved operator cleanup of retained scratch/report directories. Source/config/production state remain untouched by the controller.

The manual job retains allow_failure:false, and acceptance has identical inclusion rules plus a required needs dependency and successful receipt artifact. This follows GitLab's blocking manual-job and needs:artifacts semantics ([manual job control](https://docs.gitlab.com/ci/jobs/job_control/), [YAML reference](https://docs.gitlab.com/ci/yaml/#needsartifacts)). No remote CI Lint or project settings inspection was performed. Protected/environment-scoped SSH file variables and restricted environment access must already be enforced in GitLab; YAML alone cannot establish those server-side controls.

Local validation runs only mocked stdlib deployment/acceptance policy tests and static syntax/config checks. The actual live profile cannot be exercised offline; local pytest/runtime dependencies are not installed. See production-test-comparison.md for source evidence.
